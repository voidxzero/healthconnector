# Health Connector

Self-hosted dashboard for Android Health Connect data. Three parts: a Python server in Docker, a web app the server serves, and an Android app that is the same web app wrapped by Capacitor plus a native Health Connect sync. Modeled on the user's other project, rxmindly (`/mnt/projects/rxmindly`): same shape (server + one web codebase for web and Android), same sign-in-with-a-server-address flow. `README.md` has the user-facing setup.

## Layout

- `app.py` — the whole server: FastAPI + SQLite (stdlib `sqlite3`). Tables: `user`, `session`, `api_token`, `record`, `meta`.
- `web/` — React 19 + TypeScript + Vite + `@material/web` (Material 3 components). One codebase, web and Android.
  - `src/lib/api.ts` server address(es), auth, `withServer`-style fallback between main and local address (checks `instance_id` first), offline cache of GETs
  - `src/lib/session.ts` sign in/out, restore, and `ensurePhoneSync` (the app mints its own sync token and hands it to the native side)
  - `src/lib/metrics.ts` every metric: label, unit conversion (metric/imperial), colour slot, formatting, date helpers
  - `src/lib/data.ts` fetch hooks, units, the shared date-range filter
  - `src/components/Chart.tsx` hand-written SVG charts (bars and lines, tooltip/crosshair, keyboard); `MetricCard.tsx` a chart plus its table view
  - `src/screens/` Login, Overview, Sleep, Metrics (Activity/Vitals/Body share it), Settings
  - `android/` Capacitor project. `android/app/src/main/assets/public` is generated; never edit it.
- `web/android/app/src/main/java/app/healthconnector/` — hand-written native code (Kotlin): `HcSync` (one `spec` per Health Connect type, batching, posting, saved settings), `SyncWorker` (WorkManager, every 6 h), `HealthConnectPlugin` (Capacitor plugin `HealthConnect`), `MainActivity` (registers it).
- `Dockerfile`, `docker-compose.yml` — one image: builds `web/`, serves it from the Python server as `./static`.
- `build-apk.sh` — `./build-apk.sh` builds the **release** APK (`healthconnector.apk`, signed with the permanent key if `~/.config/healthconnector/keystore.properties` exists); `./build-apk.sh debug` builds the **debuggable** one (`healthconnector-debug.apk`) that the emulator tests below need (a release build's web view can't be inspected).
- `release.sh <version>` — bumps `web/package.json`, commits, tags `v<version>`, pushes; `.github/workflows/release.yml` then tests, builds the signed APK and publishes the GitHub release.
- `tests/test_api.py` — server tests (`python -m pytest`). CI runs them, the web tests and the native unit tests before building.
- `demo_data.py` — fills a throwaway server with 90 days of made-up data.
- `android/` and `static/` at the root are the first version (standalone forwarder app, one-page viewer). Superseded and unused; kept (source only) in the first commit. Safe to delete now: they're recoverable from git history. Ask first anyway.

## Updates and releases

- **The Android app updates itself from this repo's GitHub releases** (public, so no token). `lib/updates.ts` (ported from rxmindly) asks `api.github.com/repos/voidxzero/healthconnector/releases/latest` when the app opens, comes into view, finishes a sync (`hc:synced`) or is pulled down (forced), at most every 5 minutes otherwise; `UpdaterPlugin.java` downloads the APK (HTTPS, GitHub hosts only, redirects followed without leaking anything), checks it is this app's package, and opens Android's installer, which itself refuses anything not signed with the installed key. UI: **App updates** card in Settings (version, "Update to x", progress, install-permission prompt, app-vs-server version match using `version` from `/api/status`) and a banner on every other screen.
- **The version is `web/package.json`** and nothing else: Gradle derives `versionName` and `versionCode` (major*10000 + minor*100 + patch), the server reports it (`app-version.json` in the Docker image, `web/package.json` from source). The app and server should be on the same version; the card says when they aren't.
- **Signing key:** `~/.config/healthconnector/release.jks` + `keystore.properties` (created 2026-11-19, alias `healthconnector`, 100-year validity; never commit, never print the password, never regenerate: a new key means nobody can update). CI has the same key as the `KEYSTORE_BASE64` / `KEYSTORE_PASSWORD` repo secrets. Without a key a build falls back to the debug key, which can't update over a release.
- **Releasing:** after a committed and pushed change that affects the app (anything under `web/`), run `./release.sh <next version>`: patch for fixes and small changes, minor for features, major only if the user says so. Build and test first. Server-only or docs-only changes need no release (the server is deployed by hand). Only when the user has asked for the change to be committed and pushed.
- **Nothing has been published yet** as of 2026-11-19: no release exists, so the update check answers "No release found." `./release.sh 1.0.0` makes the first one (`package.json` is already 1.0.0, so there is no bump commit; the script just tags and pushes). A debug-signed build already on a phone must be uninstalled once before the first release APK can be installed (different signing key). The CI workflow was proven with a dry run (Actions → Run workflow): tests pass, signing works, and the APK it builds has the same version and certificate as a local `./build-apk.sh`.

## Rules that are easy to break

- **Two ways to sign in, one session table.** The browser gets an HttpOnly cookie and must send `X-HC: 1` on writes (the CSRF guard). The Android app gets the same session token in the login response and sends it as `Authorization: Bearer`; no CSRF header is needed because it isn't sent automatically. `web_user` handles both.
- **Password rules are an admin setting** (`meta` key `password_policy`: `min_length` 1–128 and four `require_*` toggles; default is length 1 and nothing required). `check_new_password` enforces them whenever a password is set (setup, add person, reset, change); existing passwords are never re-checked. The rules are public in `/api/status` so the first-run screen can show hints (`policyHint` in `web/src/lib/policy.ts`).
- **One sync token per phone per account.** The app keeps a random `deviceId` (localStorage, survives sign-out) and sends it with `POST /api/tokens`; the server deletes that account's earlier token for the same `device_id` first. Without it every sign-in added a row to "Phones sending data". `ensurePhoneSync` runs at sign-in and every app start, and makes a new token if the server no longer has the one it holds (database reset).
- **Uploads go in slices of 1000 records** (`HcSync.SLICE`): the server rejects a request over 5000 records with a 422, and one data type (months of heart rate or steps) is far more than that. HttpError now carries the server's message.
- **On-device mode (Android, no server).** `conn.mode === 'local'` (`isLocal()`): `api.get()` answers `/api/daily|records|latest` from `lib/localdata.ts`, a port of the server's aggregation (a parity check against `app.py` on 1,161 day rows matched exactly; `localdata.test.ts` covers the rules; keep both in step). Records are read from Health Connect by `lib/localsync.ts` (`HealthConnect.readRecords`, one type per call; steps, heart rate, distance and calories in 7-day windows so no single bridge reply is huge), kept in memory and in IndexedDB, and refreshed on app open/resume. A type that fails is skipped and shown (`localError()`), never silent. No token or background worker in this mode. Signing in to a server later switches `mode` to `server` and clears the local copy.
- **Sync tokens (`api_token`) can only call `POST /api/ingest`.** They are hashed in the DB and shown once. The app creates its own after sign-in and keeps it in native SharedPreferences. Never accept them on read routes.
- **Every `/api` route except `status`, `setup`, `login` and `logout` needs a session or token. All queries filter by `user_id`.** Deleting a user cascades to their data.
- **`record` is keyed `(user_id, type, start, end, source)` and ingest is `INSERT OR REPLACE`,** so resending is harmless. The phone re-reads 7 days on every sync (watches often write to Health Connect days late) and relies on this. Anything older than that, written late, is missed; Health Connect's change-token API would fix it properly.
- **Times are stored as UTC `YYYY-MM-DDTHH:MM:SSZ`** (`utc()` normalises). Per-day grouping is done in SQL with the viewer's `tz` offset in minutes; sleep is attributed to the day it *ends*, everything else to the day it starts.
- **Sum-type metrics take the largest single source per day, not the sum across sources** (phone and watch both count steps). Averaged metrics average all samples.
- **Adding a metric is four places:** `TYPES` in `app.py`; a `spec<...>` and the permission in `HcSync.kt` (plus `READ_*` in `AndroidManifest.xml`); `METRICS` in `metrics.ts`; and a screen's key list in `App.tsx`.
- **The Capacitor `Plugin` base class already has `requestPermissions`,** so ours is `requestAccess`. Plugin methods are called through `src/lib/health.ts`; keep its TypeScript interface and `HealthConnectPlugin.kt` in step.
- **Don't build a request path from `Date.now()`.** A changing URL re-fires `useFetch` forever (this happened once: an endless request loop). Use `sinceIso()`, which is stable for the day.
- **The product name is one word, `HealthConnector`** (title tag, manifest, Android `app_name`, the top bar, the sign-in heading). The mark is a heart that is also a plug (two prongs on its lobes, a pulse line through it): `web/public/icon.svg`, `components/Logo.tsx`, and for Android the vectors `drawable-v24/ic_launcher_foreground.xml` (adaptive icon), `drawable/ic_launcher_monochrome.xml` (themed icon) and `drawable/splash_launch.xml` (pre-Android-12 launch screen). Background `#00639B`. The old Capacitor PNGs in `mipmap-*` and `drawable-*/splash.png` are unused (minSdk 28 always takes the adaptive icon).
- **Pull down to sync** (`components/PullToRefresh.tsx`, `lib/refresh.ts`): server mode runs the native sync, on-device mode re-reads Health Connect, a browser just reloads. It only starts at scroll top, ignores touches in dialogs/tables/inputs, and `html { overscroll-behavior-y: contain }` stops the browser's own pull-to-refresh fighting it. Verified with a real `adb input swipe` on the emulator (screenshots taken late miss the 4-second snackbar; poll the DOM instead).
- **Every chart can be a bar or a line** (`KindToggle`, `useChartKind`, remembered per metric on the device). Sums default to bars, averages to lines.
- **Value-based colour** (`SCALES` in `metrics.ts`): per metric, ascending stops of (value, tone, word); tones are red/amber/green/blue, blended with CSS `color-mix(in oklab, …)`; bars take their value's colour, a line gets a vertical gradient along the axis. Currently sleep, steps, exercise, hydration, resting heart rate (low is blue, high is red) and blood oxygen. The tones are the status colours (`--s-critical/-warning/-good`, never themed) plus the series blue. **Colour is never the only signal**: every rated chart has a legend with the zone words and ranges, the tooltip names the zone, and the table view has a Zone column (red and green are the pair many colour-blind people can't tell apart). Thresholds are typical adult ranges, not medical advice, and are hard-coded; each card has a palette toggle to turn colouring off. To rate another metric, add a `SCALES` entry (ascending `at`; `metrics.test.ts` checks the order and that the metric exists).
- **Sync interval is a native setting** (`HcSync.intervalMinutes`, default 360, 0 = manual only; kept across sign-outs). `HcSync.schedule()` is the one place that (re)creates the WorkManager job; Android won't go below 15 minutes and may delay it. Settings → Health Connect sync has the dropdown (server mode only).
- **Haptics** (`lib/haptics.ts`, native `HapticsPlugin.java` ported from rxmindly, plugin name `HcHaptics`): crisp primitives where the phone has them, a waveform otherwise, played as touch feedback so system settings apply; `navigator.vibrate` in a browser. Used for tab/option changes (`step`), switches (`toggle`), sync results (`synced`/`failed`), chart scrubbing (`detent`) and pull-down. One switch in Settings (`hc.haptics`). Verified through `dumpsys vibrator_manager` (it logs each vibration by app).
- **Pull down to sync** shows a round indicator, a green check or red cross, a pill **toast** with the message (never a bar), and a tiny corner tick after any successful sync (`hc:synced` event, fired by the pull, Sync now and on-device reads).
- **Sleep nights are drawn as a hypnogram** (`components/Hypnogram.tsx`, `lib/hypnogram.ts`): the phone sends `extra.segments` = `[minutes after start, minutes long, d|l|r|a]` next to the stage totals. Nights synced before that existed keep the proportional `Stack` bar. `DATA_VERSION` (native) and `hc.local.v` (on-device) make everything be re-sent/re-read once when records gain detail; bump them when you add more.
- **Home screen widgets** (Android, one resizable `MetricWidgetProvider`, any number of instances, each configured): the launcher opens `WidgetConfigActivity` (a second `BridgeActivity` running the same web app), which shows `screens/WidgetSetup.tsx` instead of the dashboard because `HcWidgets.pendingConfigure()` returns the widget id; `finishConfigure` saves `WidgetConfig` (metric, layout both/number/chart, bar/line, 7/14/30 days, colour by value) and returns `RESULT_OK`. **The widget reads Health Connect itself** (works with or without a server) every ~30 minutes (`updatePeriodMillis`) and when the app asks (`HcWidgets.refresh`, after sync/refresh events). **Formatting, colours and value scales are not duplicated**: the app pushes a catalog (`lib/widgets.ts buildCatalog`: per metric label, `a`/`b` for value*a+b unit conversion, colours light/dark, tab, scale stops) at every start and when units change, and `WidgetCatalog.kt` reads it. The one thing that *is* a third copy is the daily aggregation (`WidgetData.aggregate`, beside `app.py` and `localdata.ts`); `WidgetDataTest` runs the same cases as `localdata.test.ts`. Chart bitmaps carry no text (dates are real TextViews) because the launcher stretches the bitmap. Blood pressure isn't offered (two numbers per reading). Widget icons in `res/drawable/ic_m_*.xml` are generated from `components/icons.tsx` (re-run the generator in this repo's history if icons change). Tapping a widget opens the metric's tab via `route` extra → `HcWidgets.takeRoute()`.
- **Charts follow the dataviz rules:** one fixed colour per metric (`--c-*` tokens, light/dark in `styles.css`), bars ≤ 24 px with a 4 px rounded top, 2 px lines, hairline grid, text in text tokens (never the series colour), a legend only for 2+ series, every chart has a table view. Sleep stages use blue/orange/aqua/yellow in that order (the validated adjacency).
- Layout uses `--safe-top` / `--safe-bottom`; keep them on anything pinned to a screen edge. CSP is strict (`default-src 'self'`): no CDN scripts, fonts or images.
- The Android app reaches the server through `CapacitorHttp` (native HTTP), so the server sends no CORS headers. Keep it that way. `usesCleartextTraffic` is on because home servers are usually plain `http://`.

## Deployment (the user's server)

- `docker compose up -d --build` from the project folder on the server (`/home/richard/docker/healthconnector`). Port **8000**. Data is a bind mount `./data:/data`; the folder must be owned by uid 1000 (`sudo chown -R 1000:1000 data`; `-R` matters if an older `sleep.db` made by the root container is already there) or the server refuses to start and says so.
- Only `Dockerfile`, `docker-compose.yml`, `.dockerignore`, `requirements.txt`, `app.py` and `web/` (without `node_modules`, `dist`, `android`) are needed there. Never copy over or delete the server's `data/` folder.
- The earlier version of this project was deployed with a shared `SLEEP_TOKEN` in `.env`. That variable is gone; the first visit to the page now creates the admin account.

## Testing

- **Server:** exercise it with FastAPI's `TestClient` against a scratch `SLEEP_DB`. There is no test suite checked in yet.
- **Web:** Playwright in the scratchpad against a throwaway server, as rxmindly does (`. ~/.local/opt/chromium-libs/env.sh`; `npm i playwright@1.56.1`). Type into Material text fields by setting `.value` and dispatching `input`; `page.click('text=…')` can match hidden dialog headings, so use `md-…:has-text(…)`.
- **Android:** the machine's two emulators belong to other projects (`emulator-5554` video-edit, `emulator-5580` rxmindly): don't drive them. This project has its own AVD, `hcphone` (Pixel 7, Android 16, hardware keyboard on), started with `emulator -avd hcphone -port 5590 -no-window -no-audio -gpu swiftshader_indirect` with `DISPLAY` unset. A cold boot takes ~3 minutes and ends in a "System UI isn't responding" dialog: tap Wait. From the phone the dev machine is `10.0.2.2`.
- **Driving the app:** needs `./build-apk.sh debug` (the release build's WebView is not inspectable, and it won't install over a debug one: uninstall first). The debug build's WebView is inspectable. `adb -s emulator-5590 forward tcp:9222 localabstract:webview_devtools_remote_<pid>`, then talk DevTools protocol to `localhost:9222/json` (Playwright's `connectOverCDP` does not work with Android WebViews; a ~25-line WebSocket client does). Typing through `adb emu event text` garbles fast input; set field values through the DOM instead.
- **Health Connect has no data on a fresh emulator** and the app only has read access. To test a real sync, temporarily add a plugin that writes sample records (needs `WRITE_*` permissions in the manifest and a permission prompt), run **Sync now**, check the server's `record` table, then remove it. Done once on 2026-11-18: 18 records arrived with correct values for sleep stages, exercise, blood pressure, weight, steps and bucketed heart rate.
- **Scale test (2026-11-18):** 12,000 step records and 1,000 heart-rate records (30 samples each) written into the emulator's Health Connect: the server sync sent 18,018 records in ~13 s, and the on-device read took ~13 s and charted all 83 days. That is how the 422 was caught; the earlier test had a handful of records.
- **Widgets on the emulator (2026-11-19):** added from the real launcher (Widgets → HealthConnector → Add), set up in the web screen, and re-rendered as steps bar (30 days, coloured), steps line, heart-rate number only and weight chart; tapping opens the right tab. Unit tests: `cd web/android && ./gradlew testDebugUnitTest`. The Android launcher rejects hand-made `APPWIDGET_UPDATE` broadcasts; to redraw in a test, edit `shared_prefs/widgets.xml` with `run-as`, `am kill` the app, start it and call `HcWidgets.refresh()` over DevTools (`am force-stop` leaves the app "stopped" and widgets blank).
- **Not yet verified:** the periodic 6-hour WorkManager run (only manual sync was tried), the local-address fallback on a real network, and these types end to end with real data: hydration, nutrition, HRV, body fat, height, blood glucose, breathing rate, total calories (they compile and read without errors, but no sample data was written for them). Nothing has been tried on the user's phone.
